## 1. モデルの構造

### 1.1 入力（OBSERVATION の3つの部分）
| 入力 | 形 | 中身 |
|---|---|---|
| ベクトル `policy` | 440 | 手牌・自分の状態・打牌の候補ごとのシャンテン数と受け入れ・局・席・ドラ・ルール・報酬設定 |
| イベント列 `events` | 最大 192 × 6（D-045） | 種類・相対の席・牌・付加2つ・位置 |
| 合法手マスク `mask` | 325 | 使えない行動の logit を −∞ にする（D-039） |
| 価値関数だけの入力 `critic` | 173 | 他家の手牌・ツモ山の残り・裏ドラ・他家のシャンテン数（学習時だけ） |

### 1.2 全体の形（D-048：中の案・案 A）
```
events (L×6) ─ 埋め込みの和（種類・席・牌・付加1・付加2）＋ 位置の埋め込み（欄5の位置、0〜191）
                  │
policy (440) ─ MLP → 1トークン（先頭に置く「状態トークン」）
                  │
          Transformer エンコーダ（d=256、8 ヘッド、4 層、FF 1024、pre-LN、パディングはマスク）
                  │
          先頭トークンの出力 h（256）
          ├─ 方策の頭：MLP(256→256→325) ＋ 合法手マスク → softmax
          ├─ 補助タスクの頭（§1.4）
          └─ 価値の頭：MLP([h ; MLP(critic 173 → 128)] → 256 → 1)   ← 隠れた情報は価値の頭にだけ入る
```
- **位置の情報を必ず入れる**（Q-006、D-042）：イベントの欄5（局の中の順番）を学習する位置の埋め込みにして足す。上限 192 なので表は 192 行
- 状態トークンを先頭に置く案（推奨）と、イベント列だけを Transformer に通してプールし、ベクトルの MLP の出力と結合する案がある

| 案 | 長所 | 短所 |
|---|---|---|
| A：状態トークンを先頭に置く（**採用**、D-048） | 手牌・候補の情報とイベントを注意で直接結べる（「この牌は誰が切ったか」と「自分の候補」の関係） | 系列が1つ長くなる |
| B：結合（late fusion） | 実装が単純。イベント列の部分を後から差し替えやすい | 手牌とイベントの関係を最後の MLP だけで学ぶことになる |

### 1.3 価値関数（隠れた情報）
| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| 1：共有の幹＋価値の頭にだけ隠れた情報（**採用**、D-049） | 上の図。`critic` は価値の頭の枝にだけ入る | パラメータが少ない。幹が価値の勾配からも学ぶ | 幹は方策と価値の両方の勾配を受ける（係数で調整） |
| 2：別のネットワーク | 価値関数に同じ形の別の幹を持たせ、`critic` も入れる | 方策と価値が干渉しない | パラメータと推論が倍 |

- どちらでも、方策の出力は `critic` に依らない（`critic` は方策の頭へ流れない）。漏れの検査（OBSERVATION §6）と同じ考え方で、`critic` を乱数に変えても方策の出力が変わらないことをテストにする
- 報酬は席ごと・プリセットごとに正規化した値（REWARD_CONFIG §4）。価値関数はその席の正規化した報酬を予測する

### 1.4 補助タスク
自己対戦ではラベルがただで得られる（02_RL_DESIGN）。D-050：他家の手牌・シャンテン数・聴牌と待ちの3つを重み 0.1 から始め、タスクごとの損失と全体の損失に占める割合を毎更新記録する（重みは実験で調整する）。

| タスク | ラベル | 形 | ラベルの出どころ |
|---|---|---|---|
| 他家の手牌 | 相対の席 1〜3 の種類ごとの枚数 | 3 × 34 × 5 クラス | `critic` の区画（すでにある） |
| 他家のシャンテン数 | 相対の席 1〜3 | 3 × 回帰（または 0〜6 のクラス） | `critic` の区画（すでにある） |
| 他家の聴牌・待ち | 聴牌か、待ちの種類 | 3 × (1 ＋ 34) の2値 | mj-features の `aux`（`Observation::aux`、OBSERVATION §5.1） |
| 局の結果（任意） | 自分が和了・放銃・流局 | 3 クラス | 局の終わりで付ける |

- 補助タスクの頭は先頭トークンの出力 h から出す（方策と同じ幹を鍛える）。予測そのものは推論では使わない

### 1.5 大きさと推論の見積もり［推測］
| 案 | 層 × d | パラメータ（概算） | 1サンプルの計算量（系列 192 で詰めた場合） |
|---|---|---|---|
| 小 | 2 × 192 | 約 1.5M | 約 0.25 GFLOP |
| 中（**採用**、D-048） | 4 × 256 | 約 4M（Transformer 3.1M ＋ 埋め込み・頭・MLP） | 約 1.2 GFLOP |
| 大 | 6 × 384 | 約 11M | 約 4 GFLOP |

- 計算量 ≈ 2 × Transformer のパラメータ × 系列の長さ ＋ 注意の L²·d。1局の平均は 77 件（天鳳三麻、ボット同士、OBSERVATION §3）なので、長さで分けたバッチ（バケット）にすれば平均は詰めた場合の半分以下になる
- RTX 5080（VRAM 16GB）：FP16/BF16 の実効 15〜20 TFLOPS を仮定すると、中の案で推論は**毎秒 1.5 万〜3 万サンプル**［推測］。学習（順伝播＋逆伝播で約3倍）を含めると、1サンプルあたりの GPU 時間はその 3〜4 倍
- VRAM：中の案のパラメータは FP32 で 16MB。学習のバッチ 4096 × 192 トークン × 256 次元 × 4 層の活性化は数 GB 以内［推測］。16GB に収まる
- **最初に実測する**：中の案を PyTorch で作り、バッチ 1024・4096 で推論と学習の1ステップの時間を測ってから大きさを決める

## 2. PPO の設定（初期案）と報酬カリキュラム

### 2.1 時間の単位
- 1つの判断ポイント（D-022）を1ステップとする。各席は自分の判断ポイントだけの軌跡を持つ（三麻なら1卓から3本の軌跡）
- 選択肢が1つの場面は判断ポイントにならない（D-027）ので、ステップに入らない
- 局・半荘の終わりの報酬は、その席の最後の判断ポイントの報酬にする

### 2.2 ハイパーパラメータの初期案

| エポック | 3 | 大きなバッチなので少なめ |

### 2.3 報酬カリキュラム（02_RL_DESIGN の ①→③、切り替えの目安は D-055）
| 段 | 報酬 | 対局の長さ | 対戦相手（D-052） |
|---|---|---|---|
| ①-a | 和了 ＝ +1（その他 0）。時間の要素は割引率 γ = 0.995 だけ（D-051）。ポテンシャル型のシャンテン報酬 γΦ(s′) − Φ(s)、Φ = −シャンテン数 × 0.1、その γ も 0.995 | 1局戦 | 自分自身だけ |
| ①-b | 局収支：±打点 ÷ 10000 を log1p で縮める（三麻は四麻より強く） | 1局戦 | 最新 50%・過去 50% |
| ② | 局収支 ＋ 順位点（REWARD_CONFIG のプリセット、抽選あり） | 1局戦 | 同上 |
| ③ | 終局の持ち点 ＋ 順位点（D-020）。局ごとの報酬は「局の終わりの状態から最終報酬を予測するモデル」の差分 | 半荘 | 同上 |

切り替えの目安（D-055。判定の方法は §6.3）：
| 切り替え | 目安 |
|---|---|
| ①-a → ①-b | 評価の和了率が RuleBot を上回り（最低ライン）、そのうえで直近3回の評価で伸びが止まった |
| ①-b → ② | 和了率と平均打点がともに安定し、評価での局収支が直近の最良のモデルから伸びなくなった |
| ② → ③ | 評価での報酬（局収支＋順位点）が直近の最良のモデルから有意に伸びなくなった。RuleBot に勝つことは必要条件（十分条件ではない） |
| 共通 | 放銃率・副露率・立直率が極端な値（0% など）になっていない（報酬の抜け道の兆候） |

- **切り替えは自動にしない**（D-056）。評価のプロセスが目安に達したと判定したら `runs/<実験名>/curriculum.jsonl` に書いて報告し、オーナーが牌譜を見て確認してから切り替える
- 採らなかった案：1巡ごとに −0.01（D-051 で入れないと決めた）、RuleBot に平均順位で勝つことを ② への目安にする案（RuleBot が弱すぎる。D-052 の前提）
- ①から③まで入力と出力の形は同じ（OBSERVATION は最初から③の形、02_RL_DESIGN）。報酬の計算だけを切り替える
- **段を切り替えるときは新しい実験として記録し、前の段のチェックポイントから始める**（同じ実験の途中で報酬を変えない）

## 3. 対戦相手のプールと再開

### 3.1 対戦相手のプール（D-052・D-053）
| 段 | 学習の卓の席 |
|---|---|
| ①-a | 全員が最新のモデル（自分自身とだけ打つ） |
| ①-b 以降 | 席ごとに、最新のモデル 50%・過去のチェックポイント 50% |

- 過去のチェックポイント：`save_every` 更新ごとにプールに入れ、「最新から n バージョン以内」の中から、新しいものほど重く引く（重み ∝ `decay`^(新しい方からの順番)）。過去が n 個たまるまでは、足りない分（引いた順番がまだない分）を最新のモデルで埋める
- n・`save_every`・`decay` は設定（`configs/*.toml` の `[pool]`）。初期値の案は §3.3
- 席の割り当ては対局ごとに `game_id` から決める（再開しても同じ割り当てになる）。1卓に最新のモデルが1人もいない対局は作らない（最低1席は最新のモデル）
- **学習のデータは最新のモデルの席だけ**。1卓に最新のモデルが複数いれば全員の席を使う。過去のモデルの席は方策が違うので PPO の前提（同じ方策のデータ）から外れる
- **RuleBot は学習の相手に入れない**（D-052。強さは初学者より下で、相手にすると弱すぎる）。評価の最低ラインとしてだけ使う
- **記念のチェックポイント**（D-053）：各段の最良のモデルと、`memorial_every` 更新ごとのモデルを `runs/<実験名>/memorial/` に残す。学習の相手には入れず、評価のときだけ対戦させる（過去にできていたことを忘れていないかを見る）
- 別案（採らなかった）：勝率に応じて引く（PFSP）。勝率の偏りが見えたら検討する
- 報酬設定の抽選（REWARD_CONFIG §5）は相手の席にもかかる（相手の報酬設定は相手の入力に入る）

### 3.2 チェックポイントと完全な再開
1 ファイル（または1ディレクトリ）にまとめて保存し、そこから途中で止めた状態に戻す：

| 保存するもの | 中身 |
|---|---|
| モデル | 方策・価値・補助タスクの重み |
| 最適化器 | Adam の状態、学習率のスケジュールの位置 |
| 乱数 | Python・NumPy・PyTorch（CPU・CUDA）の乱数の状態、mj-py の環境のシードと「何局目まで始めたか」（`game_index`。牌山・報酬の抽選は game_seed から決まる） |
| プール | チェックポイントの一覧（ファイル名・sha256・保存した更新の番号）、引く割合、勝率の統計 |
| 統計 | 更新ごとの統計の履歴（JSONL。§5）、カリキュラムの段、更新の回数、経過時間 |
| 設定 | 実験の設定ファイルのコピー（1実験1ファイル、REPO_LAYOUT の `configs/`）と git のコミット |

- 進行中の対局は保存しない。再開したら次の `game_index` から新しい対局を始める（途中の対局のデータは捨てる）。mj-py の `game_seed` は環境のシードと `game_index` から決まるので、再開の後も同じ牌山の列になる
- GPU の計算は完全には決定論的でないので、「再開の後に同じ数値を再現する」ことまでは求めない。「止めた時点の状態から続けられる」ことを保証する
- 書き込みは一時ファイルに書いてから名前を変える（途中で落ちても壊れたチェックポイントを残さない）。直近 N 個とプール用の間引いたものを残す
- テスト：短い学習を「止めずに回す」と「途中で止めて再開する」で、統計の履歴の行数と更新の回数が合い、プールの中身が同じこと

### 3.3 プールの n と保存の間隔の初期値（案。①-b から使う）
| 設定（`[pool]`） | 初期値の案 | 根拠 |
|---|---|---|
| `save_every` | 50 更新 | 1更新 ≈ 29 秒・約 6.5 万判断［実測：試運転、§8］なので約 25 分・約 330 万判断ごと。方策が目に見えて変わる間隔にして、ほぼ同じ相手ばかりにならないようにする |
| `n` | 10 | 窓は最新から 500 更新（約 4 時間）。過去 50% の席が「数時間前までの自分」と打つ |
| `decay` | 0.8 | 一番新しいものが過去の席の約 22%、一番古いものが約 3%（重み 0.8^j を正規化） |
| `memorial_every` | 1000 更新 | 約 8 時間ごと。評価の相手は新しい順に 3 つ（`eval.memorials`） |

- 過去が n 個たまるまでは、引いた順番がまだないぶんを最新のモデルで埋める（D-052）。最初の 500 更新は最新の割合が 50% より多い
- 1更新の時間が変わったら（最適化・モデルの大きさ）、時間ではなく更新の回数で決めているので、間隔の意味（判断の数）は変わらない

## 4. 自己対戦（Rust）と GPU の推論のつなぎ方

### 4.1 流れ（mj-py の `VecEnv` を使う）
```
loop:
  batch = env.step(decision_id, actions)      # Rust：多数の卓を並列に進め、観測を numpy で返す（GIL を手放す）
  tensors = to_gpu(batch)                    # pinned memory から非同期に転送
  logits, value = model(tensors)             # GPU：まとめて推論
  actions = sample(logits, mask)             # GPU
  rollout.append(batch, actions, logp, value)
  if rollout が満杯: PPO の更新（GPU）
```
- REPO_LAYOUT の `mj-sim`（Rust 側の推論待ちの受け渡し口）は、今の mj-py の `VecEnv` が同じ役割を持つ。別の crate に分けるかは、学習のループができてから決める

### 4.2 どこが遅くなりそうか
| 部分 | 量 | 根拠 |
|---|---|---|
| 環境（局進行＋観測） | 観測の高速化の後：1スレッド 8,203 判断/秒（130 局/秒）、24 スレッド 73,154 判断/秒（1,086 局/秒）（Windows） | ［実測］`python crates/mj-py/python/bench_random.py --tables 16 --threads 1 --seconds 30` と `--tables 256 --threads 24 --seconds 15`（一様な乱数の行動、天鳳三麻の半荘、2026-11-29）。改善前は 6,339・54,397。WSL2 は改善後を測っていない［未実測］ |
| 観測1つ | 131 µs（三麻）・147 µs（四麻） | ［実測］`obs_bench`（1スレッド）。環境の時間の大半 |
| GPU の推論（中の案） | 1.5 万〜3 万サンプル/秒 | ［推測］§1.5 |
| GPU の学習 | 推論の 1/3〜1/4 の速さ × エポック 3 | ［推測］ |
| 転送 | 1判断あたり約 5KB（イベント列 192×6×2B ＋ ベクトル 440×4B ＋ critic 173×4B ＋ マスク 325B）。5 万判断/秒で 250MB/秒 | ［推測：計算］PCIe には十分小さい |

- 見積もりでは **GPU が先に詰まる**（推論だけで環境の速さ（約 7 万判断/秒）を下回り、学習の時間も GPU を使う）。最初の対策の候補：
  1. 卓を2組に分け、片方を GPU で推論している間にもう片方を Rust で進める（ダブルバッファ。Rust は GIL を手放しているので Python のスレッドで重ねられる）
  2. 系列の長さで分けたバッチ（バケット）で無駄な計算を減らす
  3. 同じ局の中ではイベント列が後ろに伸びるだけなので、Transformer のキャッシュ（KV キャッシュ）で前の判断の計算を使い回す（実装が重いので、測ってから）
- **最初の学習のループで、環境・推論・学習・待ち（GPU の温度による待機を含む、02_RL_DESIGN）の時間の内訳を毎更新記録する**。どこを直すかはそれを見て決める（D-047 作業2の方針）

### 5.1 統計（1 更新ごと、学習する席と相手の種類ごとに分ける）

## 6. 評価

### 6.1 デュプリケート評価（02_RL_DESIGN）
- 評価用の牌山のシードの集合を固定し、学習には使わない（学習の `game_seed` とは別の名前空間から作る）
- 三麻で2つの打ち手 A・B を比べるとき、席の並びは 6 通り（AAB・ABA・BAA・ABB・BAB・BBA）を同じ牌山で回す。配牌とツモの運が相殺される
- 指標：平均順位、平均の持ち点、報酬（プリセットごと）、和了率などの統計。平均の差の信頼区間は牌山ごとにまとめてからブートストラップで出す
- 何局要るか：平均順位の標準偏差を約 0.8 として、デュプリケートで分散が半分になると仮定すると、差 0.05 を 95% で見分けるのに数千半荘［推測］。最初の評価で分散を実測して決める

### 6.2 対戦相手（D-052・D-053・D-054）
| 相手 | 目的 | 頻度 |
|---|---|---|
| 直近の最良のモデル | 伸びているか。最良のモデルの更新 | 毎評価 |
| 記念のチェックポイント（D-053） | 過去にできていたことを忘れていないか | 毎評価（多ければ新しい順に数個） |
| RuleBot | 最低ライン（学習が壊れていないか）。勝つことは必要条件で十分条件ではない | 毎評価 |

- 評価は学習と別のプロセスで、チェックポイントを読んで回す（学習を止めない）。結果は `runs/<実験名>/eval.jsonl`
- レーティング（D-054）：評価の対戦の結果（デュプリケートの組ごとの平均順位の差）から、すべての打ち手（チェックポイント・記念・RuleBot）の強さを1つの物差しで出し、`runs/<実験名>/rating.jsonl` に追記する（配信画面の「AIの強さの推移」）
