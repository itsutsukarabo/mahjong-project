# DECISIONS — 決定事項の記録

新しい決定は末尾に追記する。覆す場合は、元の項目を消さずに「変更」として追記する。

## D-001 Unity を使わない
- 過去に Claude と一緒でも Unity をうまく動かせなかった
- シーン・プレハブ・Inspector などエディタ GUI 側に状態が多く、Claude Code から見えない部分が多いのが原因
- テキストのコードだけで完結する構成を選ぶ

## D-002 FE は Web 技術（TypeScript）
- Claude Code が全体を読み書きでき、情報量も多い
- 同じ成果物を Web・Steam（Electron 等）・スマホ（Capacitor 等）に展開できる

## D-003 最初から RL で育てる。天鳳データは使わない
- 天鳳には「競合製品への応用は禁止」の条項があり、天鳳の牌譜で学習したモデルを商用ゲームに載せるのはリスクが高い
- 自己対戦なら補助タスクのラベルも無料で無限に得られる

## D-004 ルールエンジンは Rust で1つに統一する
- 学習の高速化とゲーム BE の高速化を両立できる
- 学習環境と表示用エンジンでルールの実装がズレる問題（train/serve skew）が構造的に起きなくなる
- WASM でブラウザ・Electron・スマホにも同じ実装を持ち込める
- kobalab/majiang-core は「参考実装」かつ「差分テストの基準」として使う

## D-005 三麻から始める
- 報酬カリキュラム①は4人麻雀にも流用できる形にする
- ②は順位点の傾斜を変えて4人麻雀にも流用できる形にする

## D-006 報酬カリキュラム
- ①-a 和了＝+1 → ①-b 局収支（放銃も対称、打点は圧縮）→ ② 局収支＋順位点（+30000/0/−30000、正規化）→ ③ 半荘（局ごとの報酬を予測モデルで作る）
- シャンテン報酬はポテンシャル型
- 詳細は `docs/02_RL_DESIGN.md`

## D-007 学習中にルールをランダムに切り替えない
- 1つのルールに特化させたい。モデル規模（数百万パラメータ程度）を考えても、能力を分散させない方が強くなる可能性が高い
- 別ルールはメインのモデルから追加学習で専用モデルを作る
- 保険として、ルール設定の入力特徴と全ルールを包む行動空間は最初から持たせる

## D-008 FE は 2D から始め、学習の待ち時間で段階的に 3D 化する
- 2D 版は開発者向け表示として残す

## D-009 サーバー権威型
- 牌山と他家の手牌をクライアントへ送らない
- 後で Steam 版に拡張するときに作り直しにならないよう、小規模運営の段階から徹底する

## D-010 ルールエンジンは自作する
- Phase 0 調査（`docs/research/ENGINE_SURVEY.md` の案 B）に基づく
- RiichiEnv は参考実装、および三麻の第2の差分テスト基準として**隔離環境でのみ**使う（本体の依存には入れない）

## D-011 メインの学習ルールは天鳳三麻相当
- 次点は雀魂三麻相当。すぐ切り替えられるプリセットとして用意する
- プリセットはコードではなくデータファイル（`rules/*.toml`）で持つ。各値の出典は `docs/spec/RULES_PRESETS.md`

## D-012 1局戦の配給原点は半荘と同じ
- 1局戦モードのみ飛びなし

## D-013 祝儀は実装するが RL の報酬には入れない
- 祝儀は点数とは別の帳簿（局終了時イベントの別フィールド）で記録し、`scores` には混ぜない

## D-014 牌譜形式は「独自 JSONL＋MJAI 語彙」
- `docs/spec/LOG_FORMAT.md` v0.2（レビューでの修正を反映）
- 対局全体のイベントに `kyoku_idx=-1` を使う規約を採用
- 観戦遅延はサーバーの設定とし、牌譜には入れない

## D-015 モノレポ、crate 接頭辞は `mj-`
- 構成は `docs/spec/REPO_LAYOUT.md`

## D-016 GitHub Actions で CI を回しながら進める
- プッシュ・PR ごと（Ubuntu・Windows）：fmt / clippy / cargo test / 差分テスト小規模版（固定シード）/ ゴールデンテスト / 牌譜サンプルの検証
- 夜間（Ubuntu）：差分テスト大規模版（ランダムシード）。失敗ケースは最小化して記録する
- 性能ベンチマークと GPU 学習は CI に載せない
- Node・Python・majiang-core・RiichiEnv の版は固定する

## D-017 牌山は1列（`pile`）で表す
- LOG_FORMAT v0.2 の `pile`（先頭から通常のツモ、末尾から嶺上ツモ）を承認
- 王牌の枚数はルールの定数（`wall.dead_wall`）で持ち、ハイテイの位置（`pile` の残り枚数）はそこから導く（D-026）

## D-018 シャンテン数は残り枚数を考えない定義（majiang-core 準拠）
- 残り0枚の牌を待つ形も聴牌と数える
- 残り枚数を考える版が必要なら `mj-features` 側に別の関数で足す
- RiichiEnv との差分テストでは、定義の違いを変換表で吸収する

## D-019 ルールの順位点と RL 報酬の順位点は別物
- ルールの順位点（`rules` の `points.uma` など）はゲームの精算に使う
- RL の報酬は RL の設定ファイル（`docs/spec/REWARD_CONFIG.md`）に持つ

## D-020 報酬の形
- 報酬 ＝ 順位点[順位] ＋ 持ち点の係数 ×（終局時の持ち点 − 基準点）
- 天鳳：係数 0（順位のみ）
- 雀魂 雀聖以下：段位点 ＝ 順位点 ＋（終局時の持ち点 − 初期持ち点）÷ 1000
- 雀魂 魂天：係数 0（魂天専用の順位点のみ）

## D-021 各席の報酬設定は段位の実際の分布に応じて抽選する
- 対象は雀魂が雀聖以上、天鳳が七段以上
- 抽選する場合、各席の報酬設定をその席のモデルの入力に含める

## D-022 注釈は「判断ポイント」で定義する
- エンジンがある席に選択肢（見送りを含む）を2つ以上提示した瞬間を判断ポイントとし、注釈は判断ポイントごとに1つ
- RL のエージェントが行動を選ぶ瞬間と同じ定義にする
- 仕様は `docs/spec/DECISION_POINTS.md`、`docs/spec/LOG_FORMAT.md` §6（v0.3）

## D-023 MSVC ツールチェインに移行する
- オーナーが Visual Studio Build Tools を導入した（2026-11-26 移行済み、`docs/research/DEV_SETUP.md` §2）

## D-024 crate は当面 `publish = false`、ライセンスは付けない

## D-025 ルールの実装方針
- ルールの項目はすべてフラグ（列挙値）・数値とロジックで厳密に分岐させ、将来ゲームで細かいルール策定ができるようにする
- ルールカタログ（`docs/spec/RULES_CATALOG.md`、Rust の定義から自動生成）・プリセット（`rules/*.toml`）・テスト対応表（`fixtures/rules/coverage.toml`）を持ち、すべての分岐にテストを必須とする

## D-026 天鳳三麻の未確認項目をオーナーが回答した（2026-11-22）
- 値は `rules/tenhou-sanma.toml`、出典は `docs/spec/RULES_PRESETS.md`（「オーナー確認（2026-11-22）」）
- テスト用の上書きファイル（`fixtures/rules/tenhou-sanma.test-overrides.toml`）は削除する

## D-027 判断ポイントの確認事項を承認した（2026-11-28）
- 手出しとツモ切りを別の選択肢にする（DECISION_POINTS §7-1）
- 選択肢が1つの場面は RL に見せない（学習の1歩にも数えない。§7-4）
- 海底での槓・北抜きは不可（オーナー回答 B。天鳳・雀魂とも）
- 大明槓・加槓のカンドラは、その後の打牌が通った後（ロンがなかった場合）にめくる（オーナー回答 C。天鳳・雀魂とも）。§7-3（直前のイベントが `dora`）はこれで置き換わる

## D-028 牌譜に足したフィールドを承認した（2026-11-28）
- `hora.pao`、役満の役の `{id, yakuman}`、`hora.hand.melds` に暗槓を含める、`ryukyoku.actor`、`game_end.settlement`・`game_end.tobi`
- `format_version` を上げ、`docs/spec/LOG_FORMAT.md` の変更履歴に記録する

## D-029 天鳳位の報酬は十段と同じ値にする
- 天鳳位は公式の表で pt の変動がないため、本PJの決定として十段の順位点を使う（`docs/spec/REWARD_CONFIG.md`）

## D-030 報酬の抽選は学習に使うルールと同じサービスのプリセットの中で行う
- 天鳳ルールなら天鳳七段以上、雀魂ルールなら雀聖以上のプリセットから抽選する（D-021 の対象を絞る）

## D-031 雀魂三麻の段位分布の取り方
- 統計サイトの API を10回以内だけ呼ぶことを許可する。使うのは人数・割合の数字だけ
- 取れなければ当面は四麻の比率で仮置きし、provisional の印を付ける

### 前回「どのプリセットでも使っていない値」とした項目（2026-11-28）
