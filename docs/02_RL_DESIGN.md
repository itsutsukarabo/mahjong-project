# 02 RL DESIGN — 強化学習の設計

## 基本方針

- **最初から RL で育てる**。天鳳の牌譜は使わない
- **三麻から始める**。メインのルールセットは1つに固定する（`docs/OPEN_QUESTIONS.md`）
- 学習は自宅のリソース（RTX 5080 / RAM 64GB）で回し続ける。外部サーバーで一気に回すことはしない

## 報酬カリキュラム

### ① 1局戦：和了の基礎 → 局収支
1. **①-a：和了＝+1**
   - まず和了れるようになることが目的。初期のランダムな打ち手はほぼ和了れず報酬が返らないため、単純な報酬で立ち上げる
   - 時間の要素を入れる（割引率 γ<1、または1巡ごとの小さなマイナス）。入れないと「早く和了る」動機が生まれない
2. **①-b：局収支**（和了率が安定してから切り替える）
   - 和了なら +打点、放銃なら −打点（ツモ和了は支払い分を負担者のマイナスに）
   - 打点は1万点などで割ったうえで、対数（log1p）などで大きな値を圧縮するか上限を設ける。三麻は打点が高くなりやすいので四麻より強めに圧縮する
   - 打点の比重が強すぎると速度を捨てて高い手ばかり狙うので、和了率と平均打点を並べて監視する
- 4人麻雀にも流用できるよう、人数はパラメータで持つ

### ② 1局戦：局収支＋順位点
- 終了時の得点に順位点を加算した値を報酬にする
- 三麻の順位点：+30000 / 0 / −30000
- 4人麻雀用は順位点を配列で渡す（例：+30 / +10 / −10 / −30、単位は千点）。得点傾斜の変更は設定だけで済むようにする
- **報酬は正規化する**（例：10万で割り、おおむね ±1 に収める）
- 同点時の順位の決め方（起家に近い方が上位など）をエンジン側で固定する

### ③ 半荘戦：終了時得点＋順位点
- 報酬は②と同じだが、半荘の最後にしか報酬がない
- **局ごとの報酬を作る**：「局終了時の点数状況と局数から最終報酬を予測するモデル」を別に学習し、各局の前後の予測値の差をその局の報酬にする
- この予測モデルは②までの自己対戦データで学習できる

## 全段階に共通する設計

### シャンテン報酬（ポテンシャル型）
- Φ(s) = −シャンテン数 として、報酬に γΦ(s') − Φ(s) を加える
- 素朴に「シャンテンが減ったら+」を足すと、報酬稼ぎのための手崩しなどの歪みが出る。ポテンシャル型なら最適な打ち方を変えずに学習だけを速められる

### ネットワークの入力
- **最初から③の形にしておく**。①でも点数状況・局数・人数・ルール設定の特徴を入れる（①では定数になるだけ）
- 段階を上げるたびにモデル構造を変えずに済むようにする

### 行動空間と合法手マスク
- 行動の種類は三麻・四麻・各ルールの和集合で定義する
- 非合法手は logit に −∞ を入れて確率をゼロにする

### 価値関数（critic）
- 学習時だけ使う部分なので、**全員の手牌などの隠れ情報を見せてよい**。学習が大幅に安定する
- 方策（actor）には公開情報だけを渡す

### 補助タスク
- 自己対戦ではシミュレータが全員の手牌を知っているので、手牌推定・待ち推定・シャンテン推定などのラベルが無料で無限に得られる
- 既存の手牌推定モデル（HandInferenceV37 系）の構造や多タスク設計を流用できる
- データは自己対戦でその場で生成して使い捨てる（巨大なデータファイルを保持しない）

## ルールの扱い

- **学習中にルールをランダムに切り替えることはしない**。メインのルールに特化させる
- 別ルールは、メインのルールで育てたモデルを出発点に追加学習して専用モデルを作る
- ただし保険として、**ルール設定の入力特徴と、全ルールを包む行動空間は最初から持たせる**
- 混合学習が必要かどうかは、ゲーム化の段階でデュプリケート評価により実測して決める
- ①のモデルは守備を持たない押し寄りの打ち手なので、別ルールへ移植できるのは手作りの基礎まで。押し引きは②以降で学び直す

## 対戦相手

- 最新モデル同士だけで対戦させない。過去のチェックポイントを一定間隔で保存して**対戦相手プール**に混ぜる
- 固定のルールベースボットを基準点として常に置く

## 評価

### デュプリケート方式
- 同じ牌山を、席順を入れ替えて全員に打たせる（三麻なら3通り、または6通りの並び）
- 配牌とツモの運が相殺され、必要な局数が大幅に減る
- 評価用のシード集合は固定し、学習には使わない

### 記録する統計（報酬以外）
- 和了率・放銃率・立直率・副露率・平均打点・流局時聴牌率・平均順位
- 報酬が上がっているのに副露率がゼロになる、といった「報酬の抜け道」を早期に見つけるため
- これらはそのまま配信画面に載せる

## 運用（長時間連続運転）

- **完全な再開機構を必須とする**：モデル・最適化器の状態・乱数状態・対戦相手プール・統計の履歴をまとめて保存し、途中から完全に再開できること
- GPU 温度による待機時間を計測対象に入れる
- スループット（局/秒）を最初期から計測し、ボトルネックを把握する
- 環境の局進行は Rust でスレッド並列、推論は GPU でバッチ処理、という分担を基本にする

## アルゴリズム（初期案）

- PPO を基本とする（大きめのバッチ、エントロピー項で早すぎる収束を防ぐ）
- 詳細は Phase 1 で決める
