### 所見（RiichiEnv の読解で気づいた点）
- [読解・未検証] `observation/python.rs` の `encode_kawa_overview` は赤牌を牌ID 20/24/28（= 6m/7m/8m の1枚目）で判定し、`5 + i*9`（= 6m の列）に立てている。他の箇所は 16/52/88（= 5m/5p/5s）を使っており、不整合の疑い。実行による確認はしていない。
- [読解] 4麻・3麻のどちらかで直したバグをもう片方へ手で移植する構造で、「人数はパラメータで持つ」（`02_RL_DESIGN.md`）方針と合わない。
- [読解] 和了判定でフリテン確認のたびに手牌を `clone()` する等、1局あたりの小さなヒープ確保が多い（`Vec<u8>` の手牌、`HashMap` の鳴き候補）。「1局ごとのメモリ確保を最小限に」の要件とはずれる。

- コマンド：`python -I bench_riichienv.py <game_mode> <局数> 1`（スクリプトは scratchpad、一時ファイル）

- 局数は seed 0〜19 の 20 半荘で `start_kyoku` を数えた平均から換算

### 3.2 Rust コア単体（2026-11-22 追記）[実測]
Python を通さず、riichienv-core を Rust から直接回した。観測（特徴量）は作らず、合法手の列挙
（`_get_legal_actions_internal`）と `step` だけを回す。

- ソース：`docs/research/bench/riichienv-core-bench/`（`src/main.rs`、実行スクリプト `run_bench_wsl.sh`）
- 対象：smly/RiichiEnv 0ee1236（riichienv-core 0.4.11）、`GameRule::default_tenhou()`、`skip_mjai_logging = true`
- 環境：**WSL2 Ubuntu 24.04**（Windows 11 上）、AMD Ryzen 9 9900X（12コア/24スレッド）、rustc 1.98.1、`--release`
  - Windows ネイティブでは計測できなかった（GNU ツールチェインでは getrandom のリンクに `dlltool`/`as` が要り、ビルドが通らない。`docs/research/DEV_SETUP.md` §2.2）
  - WSL から crates.io に接続できなかったので、Windows 側で `cargo vendor` した依存でオフラインビルドした
- 打ち手：全員ランダム合法手（splitmix64、スレッドごとに独立のシード）。各スレッドが独立に対局を回す（`std::thread`）
- 局数は `(場風, 局, 本場)` の変化で数えた。1局戦は1対局＝1局。半荘の局数（9.05 局/半荘）は Python 版の `start_kyoku` 数（9.05）と一致
- コマンド：`wsl -d Ubuntu-24.04 -- bash run_bench_wsl.sh "3 3000 1" "5 300 1" "2 300 1"` など（引数は `game_mode 1スレッドあたりの対局数 スレッド数`）

| 5（三麻 半荘） | 1 | 300 | 2,715 | 2.414 | **1,124** | 68,167 |
| 2（四麻 半荘） | 1 | 300 | 3,603 | 2.743 | 1,313 | 115,599 |
| 3（三麻 1局戦） | 12 | 12,000 | 12,000 | 1.302 | 9,218 | 558,507 |

所見
- **Rust 単体（1,149 局/秒）は Python 経由（930 局/秒、§3）の約 1.2 倍にとどまる**。時間の大半はエンジン自体（1 step ≈ 14.4 µs）にかかっている [実測からの計算]
- 24 スレッドで 1 スレッドの約 10.3 倍（12 スレッドで 8.0 倍）。物理 12 コアを超えた分の伸びは小さい
- 計測時間は各 1〜3 秒と短い。熱やクロックの変動は見ていない [未実測]
- 自作エンジンの性能目標の基準：**三麻 1スレッド ≈ 1,150 局/秒、全コア ≈ 11,800 局/秒（ランダム打ち）**

### 決定論の確認 [実測]
- 3麻・4麻とも、seed 0〜4 で同じ行動を与えれば MJAI ログが一致
- ただし素朴に `obs.items()` の順で乱数を消費すると、4麻 seed 1 の step 240 で**観測 dict の並び順が実行ごとに変わり**（`[3,1]` と `[1,3]`）、結果が分岐した。プレイヤー番号と合法手を整列すれば一致（1579 イベントすべて一致）
- → 自作する場合も「観測・合法手の返す順序を仕様で固定する（HashMap を外部 API に出さない）」を要件にする

## 4. 推奨：**自作する**（RiichiEnv は参考実装＋三麻の第2の差分テスト基準として使う）

### 選択肢
| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. RiichiEnv をフォーク | そのまま取り込み改造 | 三麻の局進行・役・点数・回帰テストが既にある。PyO3 も動く | ルール値が固定で、多機能なルール設定には状態機械の大半を書き換える必要。4麻/3麻の複製を1つにまとめる作業も必要。コアからログ整形・特徴量・PyO3 を剥がす必要。上流の API 変更が速く、追従かフォーク固定かの二択になる |
| **B. 自作（推奨）** | 自前の状態機械。設計は riichi-rs（ルール設定・crate 分割）、三麻の細部は RiichiEnv を参照。シャンテン表など独立した部品は Apache-2.0/MIT の条件（著作権表示・変更点の明記）を守って移植してよい | 原則1〜5を最初から満たせる。人数・ルールを設定値にできる。行動空間を全ルールの和集合で定義できる | 初期の工数が A より大きい（下記） |
| C. 完全自作（何も移植しない） | B から移植をなくす | ライセンス管理が最小 | シャンテン表などで車輪の再発明 |

### 根拠
1. **ルール設定の柔軟性が差別化の軸**（`04_RELEASE.md`）。RiichiEnv の三麻は原点 35000・聴牌料 2000・赤 5p/5s 各1・ツモ損ありがコード定数で、設定構造体にない [読解]
2. **原則5（コアは状態・合法手・遷移だけ）**に反する要素がコアに同居している（MJAI ログ・特徴量・リプレイ解析・PyO3 属性）[読解]。これを剥がす改修は、規模の点で書き直しに近い [推測]
3. **4麻/3麻の複製**（約9割同一）[実測] は「人数をパラメータで持つ」方針と構造が逆。統合するなら状態機械を作り直すことになる
4. 性能面で RiichiEnv が圧倒的な優位を持つ証拠はない。Python 込み 900〜960 局/秒・1スレッド [実測] は、自作で Rust 側に並列ランナーを置けば上回れる見込み [推測、未実測]
5. ライセンス面では A も可（Apache-2.0）。libriichi（AGPL：サーバー提供時にソース公開義務）と riichi-rs（LGPL：静的リンク・WASM 同梱時の扱いが面倒、かつ 4麻のみ）は**フォーク元として不適**

### 工数の見立て [推測]
- RiichiEnv の三麻局進行＋役＋点数＋シャンテン ≈ 6,500 行（`state_3p/*` ≈3,900 + `yaku_3p` 1,103 + `hand_evaluator_3p` 313 + `shanten` 789 + `agari` 245 + `score` 99）[実測: wc -l]
- 3麻/4麻統合の自作コアも同程度（5,000〜8,000 行）と見込む [推測]

### 自作時に RiichiEnv を使う方法（コードは取り込まない）
- PyPI wheel をテスト専用の隔離環境で動かし、三麻の「天鳳風プリセット」に一致させた自作ルール設定と、合法手・和了・点数を突き合わせる（第2の基準）
- `tests/` の回帰ケース（北ロン、搶槓、流し満貫、途中流局など）を**仕様のチェックリストとして読む**（データファイルは使わない。`126_204_0_mjai.jsonl` は出自未確認のため参照しない）

> **オーナー判断が必要**：B（自作）で進めてよいか。A を選ぶ場合は「フォーク後にコアから外す範囲」を別途決める必要がある。

- 牌山 `Shan` は `Math.random()` でシャッフルし、シードを受け取らない [読解]。→ 差分テストでは牌山を外から注入する（`Dev.Game` と同じ方法）
- 実装は同期モードあり（`_sync`）。大量実行の速度は**未実測**

### 三麻への対応 [読解]
**対応していない。** 4人前提がコード全体に直書きされている。
- `Game`：`for (l = 0; l < 4; l++)`、`% 4`、`defen: [0,0,0,0]`、`player: ['私','下家','対面','上家']`、ノーテン罰 `3000 / n_tingpai`、`zhuangfeng += jushu / 4` など
- `Shan`：牌の生成が m/p/s 1〜9 固定（2m〜8m を抜けない）、王牌 14 枚固定、北抜きの補充なし
- `hule` の `get_defen`：`fenpei = [0,0,0,0]`、ツモの支払いを3人に分配（ツモ損の概念なし）、本場は `chang * 300`
- 北抜き（抜きドラ）、チーなし、三麻のドラ表示（1m→9m）の規則はない

**三麻でも使える部分**
- 役・符・翻（`hupai`, `fu`, `fanshu`）は人数に依存しない。三麻の牌だけで作った手を渡せば比較できる
  - ドラは「表示牌」で渡すため、三麻の 1m→9m は表示牌を `m8` に置き換えて渡す（ドラ 9m）
  - 北抜きドラは majiang-core に概念がないので、比較対象から外し、自作側の「ドラ内訳」から抜きドラを除いて比較する
- ロンの基本点（`defen` の素点部分）は三麻でも同じ計算式。本場・ツモの支払いは比較しない
- シャンテン数・待ちは比較できるが、三麻では 2m〜8m がないため 4麻のシャンテンと異なりうる（RiichiEnv README の例：4麻 1 / 3麻 2）→ 三麻のシャンテンは majiang-core と比べない

### 動作確認 [実測]
LOG_FORMAT のサンプル和了（親・中ポン・ドラ2・ロン）を `Util.hule` で計算：
`hupai=[翻牌 中 1, ドラ 2], fu=30, fanshu=3, defen=5800, fenpei=[6800,-5800,0,0]`（供託1本込み）。サンプルの点数と一致。

## 6. 差分テストの組み方（案）

突き合わせは**ケース ID**（`case_id`、局進行なら `game_id`/`kyoku_idx`/`event_idx`）で行い、行の順序には頼らない（CLAUDE.md）。

```
[Rust 側 generator] --cases.jsonl--> [Node harness: majiang-core] --results.jsonl--+
        |                                                                         v
        +------------------------ expected.jsonl (Rust の答え) ------> [comparator: case_id で結合]
```

| 層 | 何を比べるか | 入力の作り方 | 4麻 | 3麻 |
|---|---|---|---|---|
| L1 手牌（純関数） | シャンテン数・待ち・和了形・役・符・翻・ロン素点 | ランダム手牌＋「面子を組み合わせて作った和了形」（ランダムだけでは和了形が出ない） | majiang-core | 役・符・翻・ロン素点のみ majiang-core。シャンテン・待ちは RiichiEnv / agari と比較 |
| L2 局面の合法手 | 打牌候補・ポン/カン/（チー）候補・立直可否・和了可否・九種九牌 | 自作エンジンの自己対戦からランダムに局面を抜く | `Game.get_*` / `allow_*`（静的関数） | ポン・カン・立直・和了のみ。北抜きは仕様テスト＋RiichiEnv |
| L3 局進行 | 局全体の結果（和了者・点数移動・流局種別・連荘・次局の状態） | 自作エンジンの牌譜を majiang 形式に変換し、`Dev.Game` で再生 | majiang-core | 対象外 → RiichiEnv（天鳳風プリセット）で再生して比較 |
| L4 公開情報 | 公開情報版牌譜から作った卓状態（捨て牌・副露・ドラ・残り枚数・点数） | 公開情報版牌譜を `Board` に流す | majiang-core | 対象外（自作の公開版リプレイの単体テスト） |
| 仕様テスト | 三麻固有（北抜き・北ロン・ツモ損方式・赤牌枚数・聴牌料・本場額など） | `SANMA_RULES_DRAFT.md` で決めた値から手書きのケース | — | 必須 |

運用案
- 失敗したケースは最小化して `fixtures/` に回帰テストとして保存する（入力・期待値とも ID 付き）
- ルール設定を majiang-core の `rule` に写す対応表を1か所に置き、写せない項目のあるケースは比較から外して件数を報告する（「比較した件数／除外した件数」を毎回出す）
- 差分テストのためにも、**自作エンジンは4麻モードを持つ**（人数パラメータ）。三麻だけだと majiang-core と局進行レベルで比較できない
