# 01 ARCHITECTURE — システム構成

## 全体像

```
                ┌──────────────────────────────┐
                │   Rust ルールエンジン（コア）   │
                │  状態 / 合法手 / 状態遷移のみ   │
                └──────────────────────────────┘
                   │            │             │
          PyO3 バインディング  サーバー組み込み   WASM
                   │            │             │
          ┌────────┴──┐  ┌──────┴─────┐  ┌────┴──────────┐
          │ RL 学習環境 │  │ 対戦サーバー │  │ FE（ブラウザ・ │
          │ (Python)   │  │ (BE)        │  │ Electron・    │
          └────────────┘  └─────────────┘  │ Capacitor）    │
                   │            │          └───────────────┘
                   └────── 牌譜（イベント列）──────┘
```

## ルールエンジン（Rust）

### 責務
- 局の状態の保持
- 合法手の列挙
- 行動を受けて状態を遷移させる
- 和了判定・役判定・点数計算
- 牌山の生成（乱数シードを外から与えられること）

### コアに入れないもの
- タイマー、通信、演出、UI 向けの整形
- 学習用の特徴量生成（別クレートに分ける）

### 設計要件
- **ルールは設定値として持つ**。三麻・四麻、赤牌の枚数、北抜き、ツモ損、祝儀などを設定構造体で切り替える
- **行動空間は全ルールの和集合で定義する**。チー・北抜きなどは常に行動として存在し、使えない場面では合法手から外れる
- **決定論的**。同じシードと同じ行動列からは必ず同じ結果になる
- **大量並列に耐える**。1局ごとのメモリ確保を最小限にし、多数の卓をスレッド並列で回せること

### 候補
- 既存の Rust 実装（例：riichienv-core。MJAI プロトコル対応、三麻対応）をフォークする
- 自作する
- Phase 0 で中身を調査して決める（`docs/OPEN_QUESTIONS.md`）

### 正しさの検証（差分テスト）
- ランダムな局面・行動列を Rust エンジンと @kobalab/majiang-core の両方に流し、合法手・和了判定・点数を突き合わせる
- majiang-core が対応していないルール（三麻固有の処理など）は、仕様書ベースの単体テストで補う

## 3つの利用経路

| 経路 | 方式 | 要求 |
|---|---|---|
| RL 学習 | PyO3 で Python から呼ぶ | 大量の局を最小コストで回す（スループット重視） |
| 対戦サーバー | サーバーに組み込む（Rust サーバー、または napi-rs で Node から） | 少数の卓を低遅延で回す |
| FE | WASM | 牌譜再生・オフライン対戦・合法手の事前チェック |

## AI 推論
- 学習済みモデルは ONNX で書き出す
- BE では ONNX Runtime の Rust バインディング、FE ではモバイル版・Web 版の ONNX Runtime を使う
- 推論はメインスレッドで行わない（Worker・別プロセス）

## 牌譜（イベント列）

### 役割
再生・対戦・学習・配信のすべてが読み書きする共通の契約。

### 要件（Phase 0 で仕様化する）
- 1局を `kyoku_start` から `kyoku_end` までのイベント列として表す
- 各イベントは `game_id` / `kyoku_idx` / `event_idx` を持ち、これだけで一意に特定できる
- 牌山のシードとルール設定を対局の先頭に含め、イベント列から局面を完全に再現できる
- 「全情報版」（学習・デバッグ用、全員の手牌を含む）と「公開情報版」（配信・クライアント用）を区別する
- 天鳳 JSON 形式など外部形式への変換は、必要になった時点で変換器として別に作る

## 対戦サーバー（BE）
- **サーバー権威型**。牌山と各プレイヤーの手牌はサーバーだけが持つ
- クライアントには、そのプレイヤーが見てよい情報だけを送る
- 人間・AI を同じ「プレイヤー」として扱い、同じ卓に混在できる
- 通信は WebSocket を想定
